### 未解決の時計比較と中断

公開初回では、ゲーム内の直前／最速記録24.2秒に対し、外部測定は24.4648秒でした。差0.2648秒が既存の許容値0.25秒を0.0148秒超え、該当項目は不合格です。表示分解能や測定開始・終了の違いはありますが、この超過の原因は未確定です。

同条件の2回目はPC側で`WinError 10055`が発生しました。途中に0fpsや61,214fpsなど成立しない測定値が含まれたため中止し、その実行からゲーム性能や合否を判断していません。時計のゲームロジックや比較閾値は変更していません。

### RAM設定による個別シナリオ

場面を再現するためにRAMへ状態を設定し、以下を検査しています。開発時の70/70記録に含まれる検査であり、入力だけの完走とは区別します。

- 一般車の接触、追い越しの重複加点防止、短い減速と復帰。
- タイトル中の時計停止、走行状態での停車中計測、ポーズ除外、直前記録と最速記録の更新。
- 時計の桁上がり、長い表示からゼロへ戻すときの消し残し防止。
- 全32コースバンク境界と周回端を含む65レコードのRAM転送。
- 既存自車3姿勢の画素一致と、既存コース・景観の保全。
- 通常8区間、遭遇イベント、高負荷景観を含む12条件での描画速度。検査基準は27fps以上。

フレームレートはエミュレートされた時間に対する更新回数です。短い測定窓では読み取り時点の影響を受けるため、一周平均や連続キャプチャの値と併せて評価してください。

## Windowsでの再実行

必要なもの：PythonとPillow、SDCC、Pasmo、Node.js、openMSX、各自で用意した対象機種のBIOS。ツールやBIOSは同梱しません。付属の制御ヘルパーはWindowsの名前付きパイプを使用します。

1. このゲームのopenMSXを終了し、リポジトリのルートで再生成ビルドを検査します。

   ```text
   python tools/check_rebuild.py
   ```

2. 専用のopenMSXとローカル制御ヘルパーを起動します。

   ```text
   node tools/emulator_host.mjs
   ```

3. 別の端末でネイティブ検証を実行します。

   ```text
   python tools/verify_encounters.py --port 18796
   ```

ヘルパーは既定で`127.0.0.1:18796`を使います。競合する場合は起動前に環境変数`OPENMSX_PORT`で変更し、検証側の`--port`にも同じ番号を渡してください。環境変数`OPENMSX_EXE` / `OPENMSX_SYSTEM_DATA`で既存のopenMSX環境を指定できます。BIOSはopenMSX側でローカルに設定します。

検証はゲームをリセットし、場面設定とキー操作を行い、結果・画像を生成します。通常のプレイと同時には実行しないでください。再実行の細かな時間値は測定窓によって変化します。結果の合否、対象ROMハッシュ、入力だけの試験であるかを併せて確認してください。

## 公開されている比較用データ

開発時の70/70検証では、旧版のROM・ソース・画像・検証記録など18点を完全保全したバックアップを使っています。

公開されている`outputs/baseline-v0.3/`は、旧版ソース・資産の最小アーカイブとネイティブ画像の2ファイルだけです。公開用の11項目の保全チェックはこの最小データを使います。開発環境の完全バックアップではなく、18点の完全保全を公開の2ファイルで再検証したという意味ではありません。

`tools/verify_drive.py`や画像比較ヘルパーは、v0.4検査から呼び出す共通処理の依存ファイルとして保持しています。旧版向けの入口をv0.4の合否判定には使用せず、上記の`verify_encounters.py`を実行してください。比較用データを絞っても、v0.4の70項目の検査カテゴリは維持しています。
